# 网关超时与换孩子的替身实测

> 这份文件是**来历**: 从旧 `docs/adr/` 的实测段移出(2026-10-17), 内容逐字保留 -- 只改过
> ADR 编号与指向旧篇哪一小节的指路, 后加的注记一律带日期. 当前口径见 [ADR-0003](../adr/0003-third-party-servers-have-their-own-caps.md), 能自己复现的判据见
> 那一篇的 `## 判据`.

## 摸清的事实(数字都是本轮实测)

用替身 server(第一次调用睡 6 秒不答,后面的照常答)量的:

| 时刻                 | 改之前                            | 改之后              |
| -------------------- | --------------------------------- | ------------------- |
| 第一次(卡住的就是它) | 0.4s `tool-timeout`               | 0.4s `tool-timeout` |
| 卡住期间重试         | 0.4s `tool-timeout`(**重试没用**) | 0.0s 拿到答复       |
| 等它转完(6s 后)再试  | 0.0s 拿到答复                     | 0.0s 拿到答复       |

第二行是这条 ADR 的全部理由:**"慢"能自愈,"卡死"不能**--而这两者在外面看起来一模一样,
都只是"没在时限内答上来".

## 决定

1. **`_request` 过线即断**:摘掉队列项之后调 `self.stop(grace=0)`,再抛 `tool-timeout`.
2. **`grace=0` 是"不等它体面退"**:先断 stdin(万一它其实在读),然后立刻 `kill` +
   `wait` 收尸;默认那条路仍是 `STOP_GRACE = 3.0` 秒(收摊时给体面退的时间).理由:卡住的
   孩子没在读 stdin,那 3 秒是白等,还算在用户头上.
3. **不新增码,不新增上报面**:模型看到的还是 `tool-timeout`;日志记一笔
   `server-down tool=... error=tool-timeout`(ADR-0008 的册子里本来就有 `server-down`).
4. **重启不用新代码**:`call_tool` 那句"死了先试着重起一次"自然接上--`stop` 把 `_proc`
   置空,下一次调用看见 `not alive` 就起个新的.

## Considered Options

- **留着它等自己转完(今天的做法)**:上表第二行;而且判定"它是不是永不回头"根本判不出来.
  否决.
- **给暖状态留一手:只在同一个孩子连着两次超时才断**:判不出来--第二次也可能只是慢.而
  早断一次的成本是重起一次握手(本机替身 0.0s,npx 有缓存也快),晚断的成本是工具面哑着.
  也因为没有"判据"可写,否决.
- **把调用超时收窄**:ADR-0003 已经拍过这条(120s 是有意的,要收紧走 `DSB_TOOL_TIMEOUT`).
  不重复拍.
- **顺手也把"答不成样"(`unexpected-response`)那条路断掉**:它至少还答了,不是卡住;
  本篇不动.

## Consequences

- **重试即恢复**(上表第二行改后):模型拿着 `tool-timeout` 再打一次就落在新孩子上.
- **代价:子 server 的暖状态丢掉**--下一次调用要重新握手.对 npx 系 server 就是再起一次
  进程(包已缓存),对"手里有会话"的 server 是它自己的事(它反正没在时限内答上来).
- **代价:同一 server 上别的在飞请求会被一起叫醒成 `tool-not-running`**(`_fail_all`
  的既有语义).扩展是一趟一块地打(ADR-0005),这种并发本来罕见.
- 超时那条路少等 3 秒;收摊那条路一个字没变.

## 判据(怎么自己复现)

```sh
# 1) 绿:超时那条码 + "重试落在新孩子上"(替身 server 的 hang 岔路是睡 60s 不答)
uv run pytest tests/test_gateway.py -q -k 'hanging'

# 2) 红(它真是这条决定撑着的):把 dsb/gateway.py 里那句 `self.stop(grace=0)` 拿掉,
#    第 1 步里那条"重试"当场变红(重试自己也会超时).
```

## 真机上量一回(2026-10-18)

这回不是替身:真配一个 npx 系第三方 server.为不动 env-up 那份环境,另写一份临时 mcp.json
(`DSB_MCP_CONFIG` 指过去),中继另起在 8799(`DSB_PORT`),工作根是个空的临时目录.

```json
{
  "mcpServers": {
    "fs": { "command": ["npx", "-y", "@modelcontextprotocol/server-filesystem", "<空目录>"] }
  }
}
```

| 量的是                          | 读数                                                  |
| ------------------------------- | ----------------------------------------------------- |
| 暖启动(包已在 npx 缓存里)       | 1.7s 起完 19 件工具(启动那行"限额"落地)               |
| 冷启动(换一个没下过的包)        | 3.9s 起完(握手档 `DSB_CONNECT_TIMEOUT` 默认 30s,够)   |
| 卡死那一下(读一根没人写的 FIFO) | 20.02s 回 `tool-timeout`(这一轮把调用档压到 20s 好等) |
| 掐掉之后立刻再要一次            | 1.70s 拿到答复 -- 重起了孩子,**包没重下**(npx 缓存)   |
| 再要一次(稳了)                  | 0.001s                                                |

日志也是替身那套形状:`server-down tool=fs error=tool-timeout` 加
`tool-fail tool=fs_read_file took_ms=20018`.

**同一轮揪出的洞**:掐掉之后进程表上多了一个 `node .../mcp-server-filesystem`,父进程是 1.
`npx -y` 的形状是三层 -- 中继 → `npm exec`(壳)→ `node <包>`(真在跑的那个);`stop()`
只 `proc.kill()` 直接孩子,壳一死孙子换了爹照样转,正是这条 ADR 要绝掉的"还在转的孩子",
只是换了一层.已改成收摊送整间会话(`start_new_session=True` 加 `os.killpg`),回归是
`tests/test_gateway.py::test_stop_reaps_the_grandchild_not_just_the_shim`(把 `killpg`
改回 `proc.kill()`,它当场变红).

修完又量了一遍(同日,同一份配置):卡死收摊后进程表上一个都不剩(改前那一个父进程是 1 的
`node` 不见了);重起 1.50s 拿到答复,链子是中继 → `npm exec` → `node`,一个不多一个不少;
中继自己收摊(`SIGTERM` 走 `finally` 里那句 `gateway.stop()`)也一个不剩.

**同一 server 上别的在飞请求(同日的第二笔)**:拿中继当客户端直接打,先后挂两件 -- A 读一根
没人写的 FIFO,两秒后 B 也读一根(调用档压到 8s 好等):

| 那件 | 何时起 | 何时收到 | 收到什么           |
| ---- | ------ | -------- | ------------------ |
| A    | 0s     | 8.02s    | `tool-timeout`     |
| B    | 2s     | 5.99s    | `tool-not-running` |

B 是 A 到点那一刻被一起叫醒的(它自己那 8s 还没到),与"同一 server 上别的在飞请求会被一起
叫醒成 `tool-not-running`"那句一字不差.日志同刻两笔 `tool-fail`(5985ms 与 8022ms).

**这条腿现在是个脚本**:`scripts/third-party-mcp-probe.py`(用法见 `docs/probe.md`) --
自己起一份临时中继量启动 / 卡死 / 重起, 并按"命令行带着临时根,却不是中继后代"查孤儿;
上面这些读数它一次跑得出来(2026-10-18 跑通: 1.8s / 8.02s / 0 个 / 1.71s, 退出码 0).
