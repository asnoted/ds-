## 真机验证(2026-10-17): 整页原样进对话

**为什么验这条**: 本篇改的是"dsb 交出一页 16000 字"与"扩展侧那一轮不再腰斩"两边**同数**.
在这之前 2026-10-11 那次探针只送过 149 行 / 5,251 字--**远在旧的两千字以内**, 所以
"两边同数"这一层其实没被碰过. 要碰它, 结果得**明显大过 2000 字**, 而且证据要落在旧闸
够不着的地方.

**设置**: `toggle: true`, `speak: true`(闸开着, 扩展自动续). 问题走真机探针
`send-page --send` 真发进对话.

**造素材**: 100 行 / 13,086 字的 ASCII 文件, 每行约 124 字, **末行只埋一个唯一标记**
`ZK-PAGE-EDGE-9931`. 先在本仓用 `read_text` 算过: 整页渲染 **13,492 字**, 末尾脚注
`(文件读完:共 100 行)`--即"一个默认页装得下", 而它是**旧两千字闸的 6.7 倍**.

**走查**: 让模型 `read tmp-page-probe.txt`, 不翻页, 抄最后一行原文与末尾脚注.

**模型答**(逐字):

    一,最后一行原文:
    100: ZK-PAGE-EDGE-9931
    二,末尾脚注原样:
    (文件读完:共 100 行)

**结论**: 13,492 字那一页**整页到了模型手里**--标记落在整页一万三千字开外, 旧的两千字
闸根本够不着它; 而模型把脚注与正文("去掉行号前缀就是那一串")都报得分明. "两边同数"
这条在本机上站住. 同一轮还顺带量出两个数: **前缀开销** 406 字 / 100 行(约 4 字/行,
含脚注), 以及**三位数行号**不被当成正文(n=2, 上一次是两位数).

**顺带**: 这一轮同时是 ADR-0005 补记 #108 的第三轮(围栏 1 条 -> `agent:继续` 恰好 1 条,
账本 20 笔痕 / 3 帧没动).

## 结论先摆

**定案:`WORK_READ_PAGE_LINES = 200`,`WORK_READ_BYTES = 16_000`,扩展侧
`MAX_RESULT_CHARS = 16_000`.**(也就是 ADR-0010 原来那组数--但现在是有据的了.)

**32000 是上界探测的结果,不是定案值**:那一档没崩(0 条失败痕,offset 每步都对),
但模型**拿到答案后仍把整个文件读完**.放宽额度不会让它更精细,只会让它更浪费.

## 扫法有一个方向错误(先记,因为下次还会犯)

本篇原先写的是"从大到小扫:16000 → 8000 → 4000 → 2000",理由是"宽松的先试,才知道
天花板在哪".**那个方向找不到上界**:要找"模型读不进去"的边界得从小往上扫;从大到小
只能回答"宽松档有没有炸".

而实测把这个问题变成了另一个:**大档没炸,那么往上加也不会炸--因为约束模型的不是
额度,是那 8 轮刹车**(ADR-0005).它在第 5 轮就收手了.所以"上界"这个问题在
32000 档就已经答完:**够高,不构成约束**.

于是往下扫(8000/4000/2000)失去意义:没有证据说需要更省.

## 二分法的天花板不是 64K:那是第三方 server 的闸(**勘误**)

本篇原先写着"上界的天花板是网关那道 64K".**那是错的**,错在把两条路当成一条:

- `cap_result` 全仓**只有一处调用**(`gateway.py:482`,`Gateway._handler`),那是**第三方
  MCP server** 的结果那条路.
- **自家五件工作工具不走它**--它们经 `mcp.py:225` 的 `text_result` 直接出门,
  `text_result` 只封装不截断.

所以 `read` 原本靠 `WORK_READ_LIMIT = 16000` 兼着的那道**内存/存储闸**,在本篇删掉它之后
**是空的**.ADR-0003 的标题是"网关给交出去的东西加上限",而自家工具从来没被那道上限管过.

**已知缺口,维护者 2026-10-08 明确决定"先不管"**:四个新上限一旦被配得比旧值大,
自家 `read` 没有总量闸(内存,storage,对话三处同时被灌).补法两条--自家也走
`cap_result`,或让自家那道的截断文案**认得翻页**(`接着读:offset=`,而不是网关那句
"已截断:原文 N 字").**本篇不拍这个板.**

**这个板由 ADR-0010 拍了(2026-10-17)**:闸落在 `ls` / `grep` 两件上,而 `read` 那条路
本来就由页预算兜住(实测见那篇的事实 1).

**所以二分没有硬天花板**,只有越撞越贵的代价.三道墙实测下来:单次预算那道人没碰到,
模型上下文那道人主动避开了,**真正撞到的是第三道--测试环境自己**.

## 撞墙记录(48000 档)

| 撞什么                                    | 结果                                                                                                                                                                                   |
| ----------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 单次预算 48000 / 每轮 48000 / 单页 700 行 | **通过**,0 条与预算相关的失败痕                                                                                                                                                        |
| 模型会不会读爆                            | **不会--它比 32000 档聪明**:3999 行的文件,它 `grep` 定位 `def f500`(得第 1997 行)再只读那 20 行,**没读完**                                                                             |
| 答案对不对                                | **三个数全对**:3999 行 / f500 在 1997 行 / 返回 `x + 500`--与造文件时的事实一致                                                                                                        |
| 页面模型上下文                            | **没碰到**(它主动用 `grep` 省了,根本没往上下文里塞大块)                                                                                                                                |
| **DeepSeek 标签页掉后台**                 | **真撞到了**:虚拟列表不挂行,`messages.*` 恒读成空(AGENTS.md 记过 2026-10-07 同一坑).修法:探针补 `page-action.py focus` 动作(`Page.bringToFront`)--任何要读页面列表的动作前都得先来一下 |

**32000 档那次"读完全文"不是预算的必然**--48000 档预算更大,它反而读得更少.所以
"放宽额度会让它更浪费"这个推论**只对那个任务成立**,不是规律.本篇原先把它写成了
一般结论,那是过度概括.

## 定案:16000 / 200 行

48000 档证明**预算给宽是安全的**(模型会自己用 `grep` 精确取点,不会顺从地读完).
所以定案仍然取 16000:同样的答案,更轻的每轮占用,而且 32000 那次"读完全文"的倾向
在更紧的预算下没出现.

**不是**因为 48000 有问题(它没问题),而是因为**没有证据需要更宽,而 16000 已经够**
--ADR-0010 那些数没变,变的是它们从"拍的"变成"验过的".

## 实测(ds-browser + 探针,2026-10-08)

同一任务问两遍(读 `dsb/work.py` 640 行,答三个具体问题),两档各跑一次.

### 16000 档(单页 200 行)

- **失败痕 0 条**.
- 模型**自己排了 `offset: 201`**(脚注给了就用),翻到 245 行收手.
- 它明确说"lines 245-264 已在前一次翻页里读到"--**正确理解了自己读过哪一段**,
  脚注三态没有误导它.
- **行号没被当成内容**:它引行号当**位置**用,且引的行号**准**
  (说 `render_page` 在 245 行,正好在那一行).

### 32000 档(单页 400 行 / 每轮 32000)

- **失败痕 0 条**;offset 每一步都对(1→201→401→601,与脚注一致).
- 三种脚注它一字不差地复述出来,还自己指出"只有后两种真的给 `offset=`"--
  **连脚注的语义边界都读懂了**.
- **但它读多了**:第 3 轮已经说"I have the answer already from lines 245-294",
  仍继续翻 601 把整个文件读完,理由是"a partial view can mislead".
  放宽到 32000 之后每页更重,**它照样读完全文**.

**上界的答案**:32000 没有让模型读不进去,也没有让它不细看--**它本来就不细看,
只是顺从地把给它的都读完了**.所以额度不是这个环节的约束.

### 顺带修掉一个真 bug(两档都跑出来的)

模型报 `dsb/work.py` 有 **625 行**,实际 **624**(`wc -l`).**脚注里那个总行数是错的,
而模型照抄了它.**

原因在 `splitlines`:用 `content.split("\n")`,而文件**以换行结尾**时那个结尾换行会多切
出一段空串,于是行数 +1.我原先的注释还写着"不丢末尾空行"--那是把"以换行结尾"
误读成了"多一行".已改为先 `removesuffix("\n")` 再切:中间的空行照旧算行,空文件回
"共 0 行".

**总数错就是模型眼里的文件错**:它拿那个数去做判断(这一档就是拿它判断"读完了没有").

## Considered Options

- **若定案成 48000**(扫到的最大档):它测得**最漂亮**--模型主动 `grep` 定位,只读 20 行,
  三个答案全对.但"预算给宽是安全的"不等于"该给宽":每轮占用是实打实的成本,而
  16000 已验够用.否决--**为不存在的问题付代价**.
- **若定案成 32000**:没崩不等于该用,而 16000 档它 2 页就收手--**同样的答案,更轻的
  代价**.否决.
- **若定案成 8000 或更小**:没有证据说 16000 有问题(三档都 0 条预算相关失败),而更小
  意味着更多次翻页(每次翻页都是一轮,占那 8 轮的额度).否决--**为不存在的问题付
  代价**.
- **按 DSH 的 2000 行取用**:那是它自己仓里的默认,不是我们的答案.实测 200 行够用.否决.
- **把上界无限抬高**(比如与网关的 64K 对齐):那等于取消这道闸,而实测证明预算这一维
  本来就不构成约束(模型自己会用 `grep` 省)--**留着一个不常咬人的闸不如留着它**,
  将来真有失控结果时它还在.否决.
- **不管模型读多了**:读全文不算错,它自己判断"要确认没遗漏".但 48000 档证明**它
  不总是读多**,所以这不是需要治的行为.否决(当缺陷处理).
- **继续往上扫到撞上下文**:48000 档模型主动避开大块,上下文墙没碰到;再往上扫只会
  遇到"模型压根不用那么多"--**扫不出信息,只烧时间与账号**.否决.

## Consequences

- **四个数有了依据**:`WORK_READ_PAGE_LINES = 200`(16000 档实证够用且模型收手早),
  `WORK_READ_BYTES = 16_000`,扩展侧 `MAX_RESULT_CHARS` 与之同数.
- **`splitlines` 不再给以换行结尾的文件多算一行**,四条测试钉住这个口径(结尾有换行 /
  没有换行 / 中间空行 / 空文件).
- **"模型会不会滥用翻页"答了,而且答案是否定的**:32000 档它读完全文,48000 档(预算
  更大)它却只读 20 行--**读多少由任务决定,不由额度决定**.原先"额度会鼓励读多"那个
  推论被 48000 档推翻,本篇已改口.**额度这一维不构成约束.**
- **8 轮刹车(ADR-0005)才是这个环节的真约束**:三档都在第 5 轮以内收手,离 8 轮还远.
- **探针多了一个 `focus` 动作**(`Page.bringToFront`):读页面列表前必须先来一下,否则
  `messages.*` 恒空(后台标签页虚拟列表不挂行).这是**测出那道墙的副产品**,也是本轮
  最容易让人白跑半小时的东西.

## 补测(2026-10-17): 各档每轮到底多少字

**样本**: `dsb/work.py` 740 行 / 25,679 字(平均每行 34.7 字). 同一份文件按三档的页设置
各走一遍, 量的是 **dsb 交出的那条结果**有多长 -- 它经扩展回灌进对话(ADR-0010 第 4 条那条
路), "扩展侧的实际入参长度"就是它, 再加一层很短的载荷外壳(TOON 与标记, 不在这里).

| 档(页设置)                   | 轮数 | 每轮字数                  | 合计   | 最大那轮 | 离扩展那道 16,000 |
| ---------------------------- | ---- | ------------------------- | ------ | -------- | ----------------- |
| 16000(200 行/页, **定案档**) | 4    | 7815 / 7963 / 8515 / 5104 | 29,397 | 8,515    | **还差 7,485**    |
| 32000(400 行/页)             | 2    | 15740 / 13581             | 29,321 | 15,740   | 还差 260          |
| 48000(600 行/页)             | 2    | 24217 / 5104              | 29,321 | 24,217   | **越过 8,217**    |

**读出来的三件事**:

1. **"这一层的闸没咬"坐实了, 而且有余量**: 定案档最大一轮 8,515 字, 离 16,000 差 7,485.
2. **定案档下先咬的是行数(200 行), 不是字节预算**: 这份文件平均每行 34.7 字, 一页 ~7.8K
   字 -- 那 16,000 字节预算只在**长行文件**(约 80 字/行以上)上先咬. 翻页的"页"因此主要是
   行数概念, 与 ADR-0010 按行翻页的选择一致.
3. **合计三档几乎一样**(29,321~29,397 = 文件 25,679 + 约 3,700 字的行号与脚注开销, 约 5.0
   字/行): **总成本由文件决定, 档只决定它分几轮给**. 这就是 ADR-0010"整页原样"的代价口径.

**顺带量到一个真洞(已单独处置)**: 量成本时把行宽拉大, 发现两处闸的**末尾那句不算在额度
里** -- `read` 一页 100 字行 / 400 行是 16,154 字, `limit=2000` 加 3 字行到 17,939;
`cap_result` 行宽 64 / 80 / 100 / 120 各 16,041 / 16,008 / 16,009 / 16,023. 而扩展那道正好
16,000 且**从尾巴上截**, 截掉的正是脚注(`offset` 的唯一来源). 这与"没触发截断"不矛盾 --
那份样本每行太短, 压根没贴到边. **修法与判据见 [ADR-0010](../adr/0010-work-tool-results-are-paged-and-capped.md)**.

**怎么复现**: 按三档设好 `WORK_READ_PAGE_LINES` / `WORK_READ_BYTES`, 从 1 起按页步进调
`dsb.work.read_text(root, "dsb/work.py", offset, 页行数)`, 把每轮的 `len(...)` 记下来.

## 真机验证(2026-10-11): 半自动路径下工具结果完整

**为什么先验这个而不是重测三档**: 三档的数字是"模型读了多少"的描述, 重测一遍
不改变任何结论; 而**半自动路径下正文还能不能完整送到模型手上**是个真风险 --
标记是短的那一串, 正文改走请求体(ADR-0010), 那条路此前没有真机证据. 而闸
**关着是缺省**, 所以它是更该先验的那一半.

**设置**: `toggle: true`, `speak` 缺省(关).

**走查**:

1. 造 149 行 / 5,251 字的 `read` 文件, **末行埋一个唯一标记** `ZK-MARKER-7731`.
2. 问"读它, 告诉我最后一行原文, 把形如 ZK-MARKER 的标记逐字贴给我".
3. 标记压进输入框不动(闸关着, 没有自动发) -- 这是半自动的预期.
4. 人按回车(设计留给用户的那一步).
5. 模型**逐字**答出末行与 `ZK-MARKER-7731`, 与文件一致. **结果完整, 没被截断.**

**顺带记一件不是缺陷的事**: 模型最后说"文件里行内容的编号和呈现行号对不上".
查下来是**造素材时我自己写错了**(149 行的文件, 末行内容写成"第150行"). 模型
发现的是我的不一致 -- 顺带说明 `read` 那条路它读得够仔细. 别把它记成产品缺陷.

> 这三条是**被否决的提案**, 不是结论. 原来写成"定案 48000 / 32000 / 8000", 在 Considered Options 段里读起来像"已决定", 差点被当成与本篇结论矛盾 -- 标题明明写着"32000 只探到没崩". 故改成"若定案成 ...".

## 真机验证(2026-10-17): 那条单行标注到了模型手上

**为什么先验这两条**: 代码侧的 501 / 500 边界走的是工具真路(`tests/test_mcp_server.py`),
但"模型收到的正文里到底有没有那串标注"从没在真机上出现过 -- 而它正是 ADR-0010 那句
"静默截断会让模型以为那就是整行"的唯一反证面. 翻页脚注同理: 它是 ADR-0010 的立意,
可"模型手里真有那句 `接着读`"这一层也没在真机验过.

**设置**: `toggle: true`, `speak: true`(闸开着, 扩展自动续). 问题用真机探针
`send-page --send` 真发进对话(ADR-0006 那两条腿之一), 两轮各一个问题.

**走查**: 让模型用 `read` 读 `.agents/skills/archify/SKILL.md`(109 行, 6 行超 500 字),
照原样回报脚注与标注. 模型答:

    (文件读完:共 109 行)
    第 3 行:...(本行超 500 字)   第 15 行:...(本行超 500 字)
    第 30 行:...(本行超 500 字)  第 31 行:...(本行超 500 字)
    第 42 行:...(本行超 500 字)  第 78 行:...(本行超 500 字)

**对得上**: 本仓 `awk 'length>500'` 数出来的正是 **3 / 15 / 30 / 31 / 42 / 78** 这六行
(945 / 633 / 911 / 754 / 570 / 623 字), `wc -l` 是 **109**. 模型不是猜的: 行号与字数分布
与文件逐一对上, 而 `...(本行超 500 字)` 那串**不在工具描述里**(它只在 `dsb/work.py`
的实现与输出里), 没读到就编不出这六行.

**翻页脚注也顺带到了**: 同一文件让模型 `--limit 48`, 它报出
`(第 1-48 行 / 共 109 行,接着读:offset=49)` -- ADR-0010 那句"它知道接着读什么"在真机上
站住; 而整份读完那一轮给的是 `(文件读完:共 109 行)`, 页比文件大的形状也在.

**顺带**: 这两轮同时是 ADR-0005 补记 #108 的真机复验(两轮各一个围栏, `agent:继续` 各
**恰好一条**, 账本 20 笔痕 / 3 帧两轮没动), 见那条补记.
