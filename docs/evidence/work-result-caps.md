# 自家工具整条闸与 grep 墙钟的实测

> 这份文件是**来历**: 从旧 `docs/adr/` 的实测段移出(2026-10-17), 内容逐字保留, 只把
> ADR 编号按新编号表改过. 当前口径见 [ADR-0010](../adr/0010-work-tool-results-are-paged-and-capped.md), 能自己复现的判据见
> 那一篇的 `## 判据`.

## 摸清的事实(数字都是本轮实测)

1. **`read` 那条路本来就有闸**:`render_page` 逐行累加到 `WORK_READ_BYTES`(16_000)就断,
   断在半路时脚注先说"字节预算截断"再给 `offset=`;单行另有 `WORK_READ_LINE_LIMIT`(500)
   这道.**任何配置下**这条路的整条结果都被页预算兜住:最多比预算多一行(预算小到放不下
   时那一行仍然给它)加一句脚注.(2026-10-17 补:换行与脚注从此也算进那笔预算,于是"兜住"
   从"预算 + 同行加脚注"收紧成**就是预算本身**,见
   [ADR-0010](../adr/0010-work-tool-results-are-paged-and-capped.md).)
2. **`ls` 没闸**:`WORK_LIST_LIMIT = 500` 只管件数,名字长度没人管.500 个各 200 字名字的
   目录项,一条结果实测 **101,999 字**.
3. **`grep` 没闸**:`WORK_GREP_LIMIT = 200` 件 x `WORK_LINE_LIMIT = 500` 字,每维都没超,
   合起来实测 **102,311 字**.
4. 这两个十万字的东西**一路都是真的**:进中继的内存,进扩展 storage,再进对话.网关那道
   64K 只管第三方 server 那条路;扩展那道 16,000 字是**回灌进对话时**才截的,截的时候东西
   已经造出来,也已经传过一趟了.
5. 所以 ADR-0010 那句"`read` 没有总量闸"**指错了件**:真正裸着的是"列"与"搜"这两件--
   它们的输出是**一列不定长的行**,而行长与件数各有一道上限,恰好谁都不管总和.

## 两条参考实现(不用它们的代码,用它们的形状)

- **pi**(`packages/coding-agent/src/core/tools/truncate.ts`):一个**共享**的截断闸,两个
  独立上限(默认 2000 行 / 50KB)**谁先到谁赢**,并**永不返回半行**;每个工具自己写
  "接着怎么办"的提示(`grep` 那句是 `Use limit=400 for more, or refine pattern`).
- **dsh**(`packages/fs/`):`read` 把上限做成显式 caps(一次 `limit` / 单行 `maxLineLength` /
  一次 `maxBytes`),结果里带 `truncatedByBytes` 标记,好让上层知道"是字节截的不是行截的";
  搜索那条路另配 **spill**--超了把整份结果落文件,内联只给一页加一句
  `Full sorted result stored at: <locator>. <retrievalHint>`.

## 判据(怎么自己复现)

- **四条测试**:`uv run pytest tests/test_work.py -q -k "caps_the_whole_result or one_result or one_read_page"`.
- **那两个坏数字怎么量出来的**:把 `WORK_RESULT_CHARS` 调到很大(等于撤掉这道闸)再调一次
  `list_dir` / `grep_tree`,看结果字数;测试里就是 monkeypatch 这个常量把闸压小,连末行
  文案一起钉.
- **参考实现**:`vendor/pi-mono`(截断闸)与 `vendor/deepseek-harness`(caps 与 spill)是按
  `AGENTS.md` 的口径落在 `vendor/`(本机装出来的东西,不进库)的浅克隆
  (`--depth 1 --filter=blob:none --sparse`,只取看的那几个目录);只用来看形状.

## 摸清的事实(数字都是本轮实测)

1. **回不来是真的**:41 字的文件(`a`×40 加 `!`),`grep_tree(root, "(a+)+b")` 跑满 6 秒
   仍在转,只能 `kill -9`.而 `WORK_FILE_LIMIT = 1_000_000`,本仓就有 51 万字一行的文件,
   够它咬.
2. **`re` 能被 `SIGALRM` 打断**(与"信号进不了 C 循环"的直觉相反):同一个模式,
   `signal.setitimer(ITIMER_REAL, 2.0)` 一装,2 秒后当场抛出来.所以这道闸不必引依赖,
   也不必开子进程.
3. **正常那趟本来就不快**:本仓上 `ERROR_` 这种模式跑完要 **3.5s**(`def ` 0.7s,
   `\breturn\b` 0.04s),早已越过 `dsb.log.SLOW_MS = 1000` 那道水印.闸不能设得太紧.

## 决定

- **`grep` 整趟(编译 + 遍历 + 逐行匹配)躺在 `WORK_GREP_DEADLINE = 20.0` 的墙钟里**,
  过线抛 `pattern-too-slow`,正文写"模式 ... 未在 20s 内搜完(换简单点的写法,或指定 path
  缩小范围)".整个中止,不给半份结果--半份结果会被当成"就这些命中".
- **装闸的手法**:`signal.setitimer` 加上一个抛 `WorkError` 的处理函数,进出各一次
  (`dsb/work.py` 的 `_deadline`).装不上就**不装**(`signal` 只能在主线程装,Windows 没有
  `setitimer`):这道闸是兜底,不是语义的一部分,少一道好过在错误的地方抛异常.
- **不换 ripgrep**:线性时间是它最硬的理由,而这条理由用十几行标准库就买到了;换它要付的
  是二进制分发(npm 那个平台包 Python 侧拿不到,依赖表里写不了一行)与方言收窄.
- **方言写进工具描述**(照 ADR-0012 的"能力差公开声明"):描述与 `pattern` 参数都写明
  "Python `re` 语法";"模式太费会中止"这句也写上--模型得知道它会被中止,才会去改写.

## Considered Options

- **换 ripgrep(ADR-0012 的候选)**:线性时间,快,模型更熟 rg 语法.否掉的理由见上.
  留个口子:哪天真要搜大仓库的速度,回来重新评估.
- **让 gateway 在 `tool-timeout` 时杀掉并重启孩子**:这是更一般的那道网(任何卡住的工具
  都能被救回来),但它救的是**整台中继**而不是这一次调用:模型要等满 120s 才拿到一个
  没头没尾的 `tool-timeout`,不知道该改什么;它还默认"能超时就该重起",而重启会丢掉子
  server 手里的状态.**记成候选**,本篇不做--同一件事在 `grep` 这一侧做得更早,更准.
  **→ 已做(ADR-0003)**:那道更一般的网补上了;`grep` 自己这道墙钟仍留着(它早得多,准得多,
  还会给模型一个能照着改的码).
- **在子进程里跑 `grep` 再 `join(deadline)`**:一样能断,但要为一件纯函数引入进程边界
  (fork/spawn,结果回传,孩子不许污染 stdout 上那条 JSON-RPC).能被信号打断就不必.
- **只给单行配预算**:`re` 咬人的地方总在某一行的某次匹配里,但逐行装表要每行两次系统
  调用,而且"这一行超了就跳过"改掉了 `grep` 的语义.整趟一道闸更简单也更诚实.
- **限制模式语法(禁嵌套量词)**:要写一个正则的小解析器,判不准就漏,判错就误伤.

## Consequences

- 模型拿到的是**能照着改**的码(`pattern-too-slow`),不是一个中继故障码;工具面也不会被
  一次调用带走.
- 20 秒是"正常那趟"的六倍(实测最慢 3.5s),误伤概率低;真误伤时模型可以指定 `path`
  分几次搜.
- **代价**:主线程以外(将来若挪进线程池)与 Windows 上这道闸不生效,退回"靠 gateway 那
  120s 加人工重启".
- `_grep_scan` 从 `grep_tree` 里分出来,只为让"编译 + 遍历 + 匹配"整段待在 `with` 里.

## 判据(怎么自己复现)

```sh
# 1) 闸跟着走:把 deadline 调到 0.3s,当场 pattern-too-slow(纯函数那层 + 工具载荷那层)
uv run pytest tests/test_work.py -q -k 'backtracking or blows_up'

# 2) 不误伤:本仓上最慢的那档(实测 3.5s)照常出命中
uv run scripts/measure-result-forms.py grep --pattern 'ERROR_' --json

# 3) 洞:41 字文件加 "(a+)+b",不设闸的入口会跑满,只能 kill.
#    现在 grep_tree 自带 20s 墙钟,所以"洞"要在 WORK_GREP_DEADLINE 调成很大时才看得到.
#    默认那个数手跑过一次:20.0s 到点抛 pattern-too-slow(测试里为跑得快用的是 0.3s 那档).
```

## 未验证项

- **真机上没试过**:这条闸是在本机 pytest 与 `python -c` 上验的,没有一次真发出去的问让
  模型写出爆炸模式.模型那侧看到 `pattern-too-slow` 之后会不会照着重写,没验.
- **20.0 这个数是从一个仓库量的**:更慢的机器,更大的仓(或网络盘)上会不会误伤,没量.
- **多线程里装不上**:目前活工具都在子进程主线程里跑,所以生效;哪天挪进线程池,这道闸会
  静悄悄退化成"不装",那时要另想办法.

## 问题

> **已处置(ADR-0010 决定 17, 2026-10-17)**: 这两处闸现在都把末尾那句**算进额度**里 --
> `render_page` 每收一行先预留这一页脚注的最长写法, `cap_result` 先算末句再按"行 + 末句"
> 砍. 于是"交出去的那一整条"就是额度本身, 下面那几笔越线读数不再成立; 它们留作"这道缝
> 长什么样"的来历. 同一天夜里 `cap_result` 又收紧一层: 一行都砍不下时在行内砍(失败回执
> 回显的模式串能有几十万字), 见 ADR-0010 决定 21.

两处闸都把末尾那句**算在额度外**:

| 闸                           | 额度按什么累加                      | 交出去的那条能到多少              |
| ---------------------------- | ----------------------------------- | --------------------------------- |
| `read` 的一页(`render_page`) | 每行 `正文 + 行号 + 2`,**换行不算** | 额度 + 换行(每行 1 字) + 1 + 脚注 |
| `ls` / `grep`(`cap_result`)  | 每行 `正文 + 1`                     | 额度 + 末句                       |

实测(各造 400~1000 行):

- `read`,100 字行 / 400 行,默认页:一页 **16,154 字**.
- `read`,`limit=2000` 加 3 字行:一页 **17,939 字**--越过 1,939 字,**那是正文,不只是脚注**.
- `cap_result`,行宽 64 / 80 / 100 / 120:各 **16,041 / 16,008 / 16,009 / 16,023 字**.

而**扩展那道闸正好是 16,000**(`src/lib/continuation.ts` 的 `MAX_RESULT_CHARS`,ADR-0010
第 4 条与它同数),`truncateResult` **从尾巴上截**:截掉的正是**脚注**--`offset` 的唯一来源;
`ls` / `grep` 那边截掉的是"收窄模式 / 换个更小的目录再列"那句.于是

- ADR-0010:"一页 `read` 的结果能原样进对话,不再被腰斩" -- 这几种形状下**不成立**;
- ADR-0010:"`ls` / `grep` 一条结果 <= 16,000 字" -- 这几种形状下**也不成立**.

**为什么一直没撞上**:ADR-0010 那两档跑的是 `dsb/work.py`,平均每行 34.5 字,200 行的默认页
只有 ~7.8K 字,离 16,000 还差 7,405;`--limit 2000` 那种形状(短行,上千行)没人真跑过.
**这是贴边才咬的洞**,不是天天咬的洞.
