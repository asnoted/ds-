# 失败留痕与现场帧的真机记录

> 这份文件是**来历**: 从旧 `docs/adr/` 的实测段移出(2026-10-17), 内容逐字保留, 只把
> ADR 编号按新编号表改过. 当前口径见 [ADR-0008](../adr/0008-failures-leave-a-trace.md), 能自己复现的判据见
> 那一篇的 `## 判据`.

## Considered Options

- **给续聊失败翻红图标**:把"结果没送到模型手上"与"中继没连上"并成同一个信号.
  后者有可恢复的探活,前者是一次性的动作失败(下一轮照样能跑),翻红会误导排查方向,
  而且红着的时候恰恰没有别的信息可看.否决.
- **把失败写进对话流或弹提示**:违房规--失败提示只在扩展侧,进度与失败都不进对话流.
- **只记一个"续聊失败"不带原因**:答不出断在哪一步,等于把控制台那一行搬了个地方.
  仍然答不出问题.
- **在选项页加一块失败痕列表**:新增 UI,不在本票必要范围内;可见信号已经有(悬停),
  重复造一个只会两处不同步.
- **续聊失败绕开去重,各记一笔**:探活每 30s,续聊每轮都可能失败,几秒就能把 20 条配额
  刷满,真正要看的前因后果被冲掉.否决.

## Consequences

- **失败痕多一个环节**.图标标题那句现在可能是"上次故障 ... / 续聊 / 输入框写不进去".
  旧记录里的 `health` / `call` / `watchdog` / `rounds` 一律照旧读得出来.
- **多了一条上报消息**(`continuation-fail` kind / `ds-/continuation-fail` type),遵守
  "三路消息各有唯一构造与解析点"与"跨边界载荷一律过 parse"的既有口径.
- **失败即留痕,行为不变**:本票只记录,不重试,不自动恢复,不改任何发送或替换行为.
- **本机工具(`send.page` 等)的失败口径不动**--它们有调用方拿错误码,仍只进控制台.
- **真机可验**:在未登录 / 禁言的页面触发一次续聊,悬停里应出现"续聊 / 没找到输入框".
  验不了就在 PR 里标**未验证**.

## 真机验证(2026-10-17):抓帧失败那条负路

`uv run scripts/page-action.py frame-fail` 连着两趟都回 `ok: true`:

```json
{
  "toggleOn": true,
  "failuresBefore": 19,
  "framesBefore": 0,
  "activeWhileReporting": "chrome-extension://.../options.html",
  "injected": "sent",
  "recorded": true,
  "framesAfter": 0,
  "restored": true,
  "failuresAfter": 19,
  "ok": true
}
```

- **痕照落**:19 到 20(最前面那笔 `{where:"continuation", cause:"探针造的失败:验抓帧负路(#106)"}`),
  而 `activeWhileReporting` 是选项页--站点标签页当时**不在前台**,抓帧那一步走不通.
- **帧没多**:仍是 0.抓帧失败对原失败路径一个字没影响(ADR-0008 决定 12 那条红线的真机证据).
- **跑完原样**:探针造的那笔痕撤掉(它只是一次验证;留在册子里会一直挂在选项页的
  "上次故障"上--真探活只在由红转绿那一下补恢复时刻),`failuresAfter` 回到 19.
  两趟连着都绿,说明这道判据可重复.

**顺手记一个坑**:background 手里那份留痕是**内存副本**,只在总开关键变时才从
`storage.local` 重读(`syncFromStorage`).所以"直接往 storage 写一笔假痕"这种做法,
改的只是 storage,内存那份没动;而 `rememberFailure` 的口径是"最前面那笔还没恢复就
不新起一条",于是**下一笔真痕再也落不下来**,探针会一直报 `recorded: false`,而错的
是探针.`frame-fail` 因此跑完扳一下总开关(关,再开)让两边对齐--这一步住在探针里,
不写进产品:产品手里那份本来就该跟着开关走.

**加固(2026-10-17 晚,同一个坑的另一半)**: "撤探针那笔痕"的第一版判据是"最前面那笔
是我们的**且总数 +1**".上面那两趟记着 19 → 20,那是在册子没满的时候;等册子满到 20 笔
(上限 `FAILURE_LOG_CAP = 20`),新痕进来会把最老那笔挤掉,**总数根本没变**,判据永远
不成立--`restored: false`,探针的痕就一直挂在选项页的"上次故障"上(撤不掉的不止它,还有
被挤掉的那笔真痕).改成 `sole_new_trace`:最前面那笔是我们的,且**其余各笔与跑之前逐笔
相同**(按 `at` 序列比,`recoveredAt` 不算动).真机复验:

- 上一趟剩的那笔探针痕:进去先撤(`healed: true`,19 笔),按原样重来;
- 这一趟的痕照落,帧仍没多(2 → 2),`restored: true`,册子上**一笔探针的痕也不剩**.
