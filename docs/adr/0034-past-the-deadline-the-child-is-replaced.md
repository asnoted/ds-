# ADR-0034: 过了时限就换一个干净的孩子:网关超时即断掉子进程,重试起新的

- **Status**: accepted
- **Date**: 2026-10-17
- **Supersedes**: none

**只修订 ADR-0016 的一点**:它拍的三档超时(握手 30s / 发现 20s / 调用 120s)一个字不改,
本篇拍的是**过了那条线之后干什么**--今天只是把待收的队列项丢掉,那个还在转的孩子原样留着;
改成当场断掉,让下一次调用起个新的.

**兑现 ADR-0033 记下的候选**:那篇在"Considered Options"里把这条记成候选(它救的是整台中继,
不是这一次调用).现在补上;`grep` 自己那道墙钟仍留着--它早得多,准得多,还会给模型一个能
照着改的码.

## 问题

adr-0016 把超时定成了"判一个码",没定"判完怎么收场".今天的收场是:

1. `_request` 过线只做两件事:把待收的队列项摘掉,回 `tool-timeout`.
2. 孩子**照转**(它没在读 stdin,断不了);`call_tool` 那句"死了先试着重起一次"只在
   `not alive` 时动手,而"忙"不是"不 alive".
3. 于是卡住期间**每一件工具都排在它后面**,各自等到自己的超时.它要是永不回头(第三方
   server 死锁在某个网络调用上),工具面就一直哑着,只能人来重启中继.

## 摸清的事实(数字都是本轮实测)

用替身 server(第一次调用睡 6 秒不答,后面的照常答)量的:

| 时刻                 | 改之前                            | 改之后              |
| -------------------- | --------------------------------- | ------------------- |
| 第一次(卡住的就是它) | 0.4s `tool-timeout`               | 0.4s `tool-timeout` |
| 卡住期间重试         | 0.4s `tool-timeout`(**重试没用**) | 0.0s 拿到答复       |
| 等它转完(6s 后)再试  | 0.0s 拿到答复                     | 0.0s 拿到答复       |

第二行是这条 ADR 的全部理由:**"慢"能自愈,"卡死"不能**--而这两者在外面看起来一模一样,
都只是"没在时限内答上来".

## 决定

1. **`_request` 过线即断**:摘掉队列项之后调 `self.stop(grace=0)`,再抛 `tool-timeout`.
2. **`grace=0` 是"不等它体面退"**:先断 stdin(万一它其实在读),然后立刻 `kill` +
   `wait` 收尸;默认那条路仍是 `STOP_GRACE = 3.0` 秒(收摊时给体面退的时间).理由:卡住的
   孩子没在读 stdin,那 3 秒是白等,还算在用户头上.
3. **不新增码,不新增上报面**:模型看到的还是 `tool-timeout`;日志记一笔
   `server-down tool=... error=tool-timeout`(ADR-0004 的册子里本来就有 `server-down`).
4. **重启不用新代码**:`call_tool` 那句"死了先试着重起一次"自然接上--`stop` 把 `_proc`
   置空,下一次调用看见 `not alive` 就起个新的.

## Considered Options

- **留着它等自己转完(今天的做法)**:上表第二行;而且判定"它是不是永不回头"根本判不出来.
  否决.
- **给暖状态留一手:只在同一个孩子连着两次超时才断**:判不出来--第二次也可能只是慢.而
  早断一次的成本是重起一次握手(本机替身 0.0s,npx 有缓存也快),晚断的成本是工具面哑着.
  也因为没有"判据"可写,否决.
- **把调用超时收窄**:ADR-0016 已经拍过这条(120s 是有意的,要收紧走 `DSB_TOOL_TIMEOUT`).
  不重复拍.
- **顺手也把"答不成样"(`unexpected-response`)那条路断掉**:它至少还答了,不是卡住;
  本篇不动.

## Consequences

- **重试即恢复**(上表第二行改后):模型拿着 `tool-timeout` 再打一次就落在新孩子上.
- **代价:子 server 的暖状态丢掉**--下一次调用要重新握手.对 npx 系 server 就是再起一次
  进程(包已缓存),对"手里有会话"的 server 是它自己的事(它反正没在时限内答上来).
- **代价:同一 server 上别的在飞请求会被一起叫醒成 `tool-not-running`**(`_fail_all`
  的既有语义).扩展是一趟一块地打(ADR-0015),这种并发本来罕见.
- 超时那条路少等 3 秒;收摊那条路一个字没变.

## 判据(怎么自己复现)

```sh
# 1) 绿:超时那条码 + "重试落在新孩子上"(替身 server 的 hang 岔路是睡 60s 不答)
uv run pytest tests/test_gateway.py -q -k 'hanging'

# 2) 红(它真是这条决定撑着的):把 dsb/gateway.py 里那句 `self.stop(grace=0)` 拿掉,
#    第 1 步里那条"重试"当场变红(重试自己也会超时).
```

## 未验证项

- **真机上没制造过第三方 MCP server 卡死**:这条是在替身 server 上量的.真配着 npx 系
  server 卡住时会怎样(重启要多久,包里有没有要重下的东西)没量.
- **并发那条只在代码上读出来**:扩展一趟一块地打,造不出"别的在飞请求被一起打断"的现场,
  所以那条代价是读代码得出的,不是实测.
- **"永不回头"没构造出来**:替身是"睡 6 秒",能自愈;真正永不回头的孩子(死锁)没有替身,
  上表第三行那格是"等它转完"而不是"它永不来".
