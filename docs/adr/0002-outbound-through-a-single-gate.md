# 所有出站经唯一出站口,开窗 3~5 秒

- **Status**: accepted
- **Date**: 2026-09-29
- **Supersedes**: none

扩展往页面发的每一条消息都要过同一个出站口,窗口开启时一次性发出,窗口之间随机等 3~5 秒;不逐条连发,不做固定短间隔的节流.

依据是 2026-09-26/28 的实测(原 issue #8):一轮 7 次工具执行产生 6 条回灌,**每条间隔都合规**(3.8s/5.0s/3.7s/3.4s/2.3s/15.4s),末尾仍然撞上 `finish_reason: rate_limit_reached`,模型的收尾回答被整个吃掉,随后账号被阶梯处罚禁言 3 天.结论是:**节流合规 ≠ 不会被限流,减少消息条数本身是独立的必要措施**--所以真正的单位是"发了几条",不是"隔了多久".

## Considered Options

- **逐条发送 + 固定间隔**:实测已证伪,间隔合规照样撞限流.
- **三态状态机**(正常 / 长休 / 退避,处理阶梯处罚):~~旧设计需要它,是因为一轮会发 7 条;现在单来回恒为 1 条,状态机没有负载支撑,押后到真撞限流再做.~~ **这条已经作废,2026-10-03 记**:出站口落地之后账号仍然被禁言,而且**刑期从 3 天加到 8 天**(第二次"禁言至 2026-10-10 20:21").当时押后的理由是"一轮恒为 1 条,状态机没有负载支撑"--**负载不是那 7 条回灌,是阶梯处罚本身**:真实负载是"已经在处罚区",而状态机处理的正是这件事.所以"等真撞限流再做"的条件已满足,退避不再是可选项.
- **不节流**:账号已在阶梯处罚区,代价是实测付过的.

## Consequences

- 出站口是扩展里唯一的发送路径,`CONTEXT.md` 的"唯一出站口"与"出站窗口"两条词条即由此而来;新增发送需求只能排进队列,不能绕开.
- 单来回下队列恒只有一个元素,**用户插话与在途回灌的顺序**(旧 `#8` 的 user story 18)押后到支持多块时再定.
- 合并后的消息更长,**站点是否对单条消息长度另有判据**未实测(原 `scripts/cdp-maxlength.mjs` 已随历史清除,需要时重建量法).
- **唯一出站口没有解决禁言**(2026-10-03 补记):实测两次禁言后,本 ADR 头号结论"真正的单位是发了几条"显然不足--出站口把一轮压成 1 条,账号照样进处罚区,且刑期逐次加重.**没搞清的是站点判的是什么**:可能与出站口无关(登录/会话/并发/内容特征),也可能条数只是必要条件之一.这条不能再拿"已按 ADR-0002 修过"当挡箭牌,退避要独立设计,不指望它已被覆盖.
- **"唯一的发送路径"只对自动续聊成立**(2026-10-05 补记,issue #48):上一条说"出站口是扩展里唯一的发送路径,新增发送需求只能排进队列,不能绕开"--**实测已绕开过**:看门狗催办(`deliverNudge`)与本地工具 `send.page` 都走 `runAction` → `page.ts` 的 `writeComposer` + `pressEnter`,**不经 `gate.ts`**(`grep "from .../gate"` 全仓只有 `inject.content.ts` 一处).所以 3–5 秒窗口对它们无效,一次 `send.page` 与一次续聊能在 1 秒内连发两条.
  本 ADR 的决定本身不推翻(窗口仍然只管续聊那一路,它是对的),但**"唯一"这个说法当时是错的,现在也是错的**:`CONTEXT.md` 的两条词条与 `conventions` spec 已按"续聊这一路的收口"改对,出站窗口的真实约束范围以 `continuation` 能力为准.要不要把另两条路也收进来是另一个决定(跨世界重构出站口,风险与收益不匹配--那两条路本来就有闸,只是没有窗口限速).
- 禁言的**代价是整条交流线断掉**:站点不渲染写作框,写动作全部无效(扩展侧已能认出处境,见 `page.state` 的 `account` 与 ADR-0010).所以"少发几条"不是体验问题,是能不能开工的问题.
