# ADR-0023: "代你发言"闸只管发送;闸关着时自动续聊变半自动

- **Status**: accepted
- **Date**: 2026-10-08
- **Supersedes**: none

本篇**修订 ADR-0014 的一点**(它那条"续聊有自己的刹车,催办受 `speak` 管"的分工),
并把"代你发言"闸的语义收窄.ADR-0014 与 ADR-0002 **不因此改动**--回灌机制与出站口
本身都没动.

## 问题

`speak` 闸叫"代你发言",原先管的是"动写作框的"动作(`composer.type` /
`composer.clear` / `send.enter` / `message.retry` / `button.click`).但用户关掉它之后:

- 看门狗催办停了 ✓,`send.page` 停了 ✓,
- **自动续聊照跑**--工具结果每轮回来,仍往用户账号里塞一条真实用户消息.

从选项页看到的因果是"我关了'替我说话',它确实不催我了",合理推断是这条闸管着所有
代替我发言的行为.实际不是.续聊在 MAIN 世界直接操作 DOM,**不经 `runAction`**,
而 `speak` 键**从不跨世界传递**(状态消息只带总开关),那个世界压根拿不到这个值.

## 决定

1. **闸的语义 = "是否允许替你把消息发出去"**.受闸的是所有**发送**:`send.enter`,
   发送态的圆键,`message.retry`,看门狗催办的发送,自动续聊的发送.`composer.type` /
   `composer.clear` **出闸**--往输入框里写字不叫替人开口.
2. **`speak` 跨世界**.隔离世界每次广播开关状态时一并带上,MAIN 世界按它决定自动发
   还是只落草稿;选项页勾选**即时生效**(改 `storage` → 立刻再广播,不必刷新页面).
   缺字段的旧信封按**关**处理(保守:宁可等用户按).
3. **闸关着时自动续聊变半自动**:不按 Enter,不点发送键,只把短标记**写进输入框**,
   等用户自己按发送.用户随后发出的那条,正文逐字等于标记 → 被换成工具结果
   (沿用 ADR-0020 的钥匙).
4. **待发续聊没有期限**.钥匙使时间不再是安全判据(用户手打的话永远不等于标记),
   所以"等多久都安全";它是**单槽**,新一轮顶掉旧的.失效条件只有五条:被消费,
   被新一轮顶掉,换了页面会话,总开关关掉,用户发出了别的话(钥匙不符).
5. **输入框里有你的草稿就不覆盖**:这一轮作废,留一笔失败痕(`draft-in-composer`).
   与"宁可少一轮,也不能吃人说的话"同源.
6. **看门狗催办闸关着时整个跳过**(不写,不发)--它是"写 + 发"成对的动作,只写不发
   会在你的输入框里留下半截"继续".跳过即不算催,计数不动.
7. **`send.page` 写步放行,发送步被拦**,回现有的 `disabled`(**不新增失败码**),
   那条问题留在输入框当草稿.原来的两步步序照走,行为自然落成这个.
8. **写输入框不再受闸,意味着协调者能覆盖你正在打的草稿.** 这是维护者明确接受的
   取舍,**选项页文案如实写明**(原先那句"不会碰你正在打的东西"不再成立,删掉).
   本票**不加**覆盖保护(续聊那条路径除外,见第 5 条).
9. **选项页加一行"上次故障"**:读既有的失败痕(ADR-0004),**不新增任何上报**.
   8 轮到顶(环节 `rounds`)与续聊那一跳的各种失败(#51 的 `continuation`)都能在那里
   看见,不必翻控制台.
10. **`composer.type` / `composer.clear` 仍在退避闸下**:它们是写动作,账号在处罚区时
    照拦.原先它们是靠"在 `speak` 名单里"顺带进的退避闸,语义换了以后必须**显式**
    列进 `BACKOFF_GATED_ACTIONS`,否则会跟着漏.

## Considered Options

- **维持原状(续聊不受闸),只在选项页补一句文案**:用户仍然可能在不知情的情况下被
  塞消息.选项页那一句谁会读?--而"代你发言"这个名字就在复选框上.否决.
- **`speak` 关着就停续聊**:总开关单独开着会**什么都干不了**,两个开关实际合并成一个,
  "接管页面"与"替人开口"的分工就没了.半自动是更细的粒度:**接管照旧,只把最后
  一步交给人**.否决.
- **半自动下让协调者仍然自动按发送,只是不写长正文**:那还是替人发言,闸形同虚设.否决.
- **半自动时把短标记换成一句更明显的话**(如"(扩展要发的工具结果,按发送)"):
  会把 TOON 载荷的痕迹摆进可见流,与 ADR-0014"可见的只剩两行"相悖.否决.
- **把待发续聊也设一个 TTL**:钥匙落地后时间不是安全判据,设不设都不影响安全性,
  只会在用户没立刻按的时候白作废一轮.否决.
- **闸关着时往输入框写**"续聊中..."**之类的提示占位**:占位本身就是替人写输入框,
  还要多一套清理逻辑.否决.

## Consequences

- **默认体验变了**:`speak` 默认关,所以**默认情况下自动续聊从全自动变成半自动**.
  这是有意的行为变化,已写进 PR 描述.是否该默认开是另一个产品决定,不在本票.
- **三个开关的分工现在各自独立**:总开关 = 是否接管页面(续聊的授权);`speak` = 能否
  替你发出;退避 = 账号在处罚区时暂缓写动作.闸关着不是停摆,是**只落草稿**.
- **`SPEAK_GATED_ACTIONS` 与 `BACKOFF_GATED_ACTIONS` 不再互为子集**(第 10 条),
  两张名单都要显式维护,新增动作要分别想清楚.
- **选项页不再承诺"不会碰你正在打的东西"**.想恢复那个保证需要另加覆盖保护
  (不在本票).
- **失败痕多一个可见处**:选项页的"上次故障"与图标悬停读同一份记录,两处同源.
- **旧 ADR 一字未改**:ADR-0014 那条分工描述的仍是"刹车 vs 闸"的归属,
  本篇改的是闸**管什么**以及续聊在闸关着时的形态.

## 真机验证(2026-10-11): 这一条最要紧的 AC 已跑通

**设置**: 扩展总开关打开, `speak` **关着**(即 `storage.local` 里没有 `speak` 键,
`readSpeak(undefined)` = 关). 账号 ready, 未禁言.

**走查**:

1. 问"用 read 工具读一下 README.md 的第一行, 然后告诉我那一行是什么"并回车.
2. 会话区出现模型发出的工具调用, **紧凑 JSON**(正是 #93 的形态):
   `{"tool":"read","arguments":{"path":"README.md","limit":1}}`
3. 中继执行完 `read`, 结果回到扩展 -> 续聊该走哪一路由 `planContinuation(speak)`
   判. `speak` 关着 -> 落 `stage-only`.
4. **写作框里出现 `agent:\n继续`, 并且连续 70 秒没人按它**: 模型那边停在等续聊
   (最后一条气泡仍是工具调用, 没有最终答复), 写作框里那串标记没动.
   **这就是"闸关着时只落草稿,不按发送"的真机证据.**
5. 按下回车(这一步是设计留给用户的) -> 标记被认成钥匙(#49), 工具结果带回去,
   模型给出最终答复: "README.md 的第一行是: `# ds-`".
6. 独立核对 `head -1 README.md` = `# ds-`, **与模型答的逐字一致** -- 不是模型编的.

**顺带验到的**: #49 的钥匙(短标记被认出并换成工具结果),#93 的紧凑 JSON 形状,
中继 -> 扩展 -> 站点这一整圈往返.

**怎么开总开关**: `page-action.py storage set --data '{"toggle":true}'`. 真源就是
`storage.local`, 写入触发 background 的 `storage.onChanged -> syncFromStorage`,
与产品路径的 `toggle.set` 走同一条路. 判据读**钩子装没装**(内容脚本 `apply(true)`
会替换 `window.fetch`), 别只读 storage -- 那是真源, 不是效果.

## 真机验证(第二跑, 2026-10-11): 闸**开着**的那一半

同一设置只把 `speak` 打开(`storage set --data '{"toggle":true,"speak":true}'`),
问"用 read 工具读 GLOSSARY.md 的第一行, 只读一行, 然后告诉我那一行".

**全程没按回车**: 从回车到模型给出最终答复, 探针只做了"读页面", 一次 `send.enter`
都没再发. 会话区最后一条是"GLOSSARY.md 的第一行是: `# ds-`", 写作框是空的.

独立 `head -1 GLOSSARY.md` 核对, 逐字一致.

**与第一跑的对照才是证据**:

| `speak` | 写作框                          | 要不要人按回车       |
| ------- | ------------------------------- | -------------------- |
| 关      | 压着 `agent:\n继续` 不动, 70 秒 | 要人按, 按了模型才续 |
| 开      | 空                              | 没人按, 模型自己续完 |

**这才是闸的两半**: 同一段代码, 只因 `planContinuation` 收到的 `speak` 不同,
一支落草稿,一支自动发. 前一版只有单测钉住 `stage-only` 那一支"没有发送动作",
现在两支都在真机上各自走了一遍.

**顺带**: `speak` 写进 storage 后**不必重载页面**下一次决策就生效, 这条路与
`toggle` 同源(`storage.onChanged → syncFromStorage`), 上面那条"勾选即时生效"
验的就是它.

## 真机验证(2026-10-17): `send.page` 的两步真的按序跑了

**(勘误,同日晚:下面这份证词取自 `#1792211431` 那一趟,而那一趟**撞上了扩展自己的续聊**--
它不算干净;干净的一趟,以及探针因此改的两处,见文末"勘误与加固"段.)**

**设置**: 总开关开着, `speak` **开着**(人勾的那把闸, 探针只读不碰), 当前是一条新开的
空对话. `uv run scripts/page-action.py send-page --send` 连着两趟都回 `ok: true`:

    { "toggleOn": true, "speak": true,
      "question": "真机探针:收到就只回两个字--收到(#1792211431)",
      "landed": true, "sawDraft": true, "composerAfter": "",
      "rowsSeen": 9, "continued": true, "ok": true,
      "verdict": "问题以用户消息进了对话:composer.type 与 send.enter 两步都跑到了" }

**这三件一起才算这一步跑到**:

1. **第一步真写进了写作框**(`sawDraft`):同一趟里先看见写作框压着那条问题,再看见它进对话.
2. **第二步真按了发送**(`landed`):那条问题以 `user` **原样**进对话,写作框随之空
   (`composerAfter` 是空的).两条路都过 `runAction` 的三道闸--这一趟闸开着,所以放行.
3. **工具结果顺 回灌 那条路自动续了一轮**(`continued`):对话里跟上一条 `user`
   `agent:\n继续`(短标记)与模型的答复,即 ADR-0013 决定里"结果按回灌口径回页面"
   那句在**本地工具**上的真机面.

**判据要两条一起看**:只看"写作框里有那条问题"会把"发出去之后写作框还没来得及空"读成草稿;
只看"对话里有那条问题"认不出那是哪一轮排的(所以问题带 `#时刻`,**按整条**比,
别认"看到过某个词").

**踩到的坑(第一趟假绿)**:探针原先从 storage 读发言闸时漏读了 `speak` 这个键,
`stores.get("speak") is True` 于是把"闸开着"读成"闸关着";它又在**第一次**读到写作框
里还是那条问题时就收了手.两个错叠起来:一条**真发出去**的问题被当成了"闸拦下的草稿",
判据假绿(独立核对:那趟的问题确实在对话里,那趟的选项页也记着 `speak: true`).
改法两条--`speak` 加进那份读取表,且**一律把 `SEND_PAGE_WAIT` 等满**:探针分不出
"还没发"与"不会发",半路收手就是把"观测漏了"当事实(`probe.md` 那条纪律).

**机器状态**: 跑完写作框空,圆键回到发送相;那条问题与它带来的续聊留在对话里
(探针不代删,`continued` 是等它落地才收手--别的探针最怕跑到一半撞上续聊).

**闸关着那一半还没验**: 要人把"替人开口"关掉再跑一次 `send-page`(不给 `--send` 也行),
那时的判据是"问题**留在写作框**,对话里没有",且探针会把那笔草稿清掉.
agent 不代勾也不代关,所以这一趟只能等人.

## 勘误与加固(2026-10-17 晚): 探针打字会撞上扩展自己的续聊

**那次相撞**: `#1792211431` 那一趟打字的那一刻,扩展正把它上一轮工具结果的**短标记**写进
写作框(`agent:\n继续`)待着限速;探针那一下把它顶掉了,扩展出站时认不回自己的标记,
于是账本上多了一笔 `continuation` / `key-mismatch`("发出去的正文不是等你的那条短标记
(可能被打字盖掉了)"). 那情形下**"两步"的归属本来就分不出来**--问题确实进了对话,
但按发送的那一下可能是扩展自己(它随后也按了 Enter). 判据当时给的绿,不算数.

**干净的一趟**(问 `read` 工具读 `GLOSSARY.md` 第一行,闸开着):

    { "landed": true, "sawDraft": true, "composerAfter": "", "continued": true,
      "failuresBefore": 20, "failuresAfter": 20, "framesBefore": 2, "framesAfter": 2,
      "ledgerClean": true, "ok": true,
      "verdict": "问题以用户消息进了对话:composer.type 与 send.enter 两步都跑到了" }

**探针因此改了两处**:

1. **打字前先盯 6 秒写作框**(`SEND_PAGE_IDLE_WATCH`): 扩展的续聊是"先写短标记,待一段
   限速,再按发送",那段待限速就是它压在写作框里的窗口(最长 15 秒). 写作框里一有字
   (你的草稿,或它那条标记)就打 `blocked` 退 4,不碰--**顺带也就保住了人正在打的草稿**.
2. **跑完对账本**(`ledgerClean`,并进 `ok`): 这一轮多出一笔失败痕/现场帧就不算绿.
   算不出来的归属那笔,多半正说明"扩展那一步的发送被算到了 `send.page` 头上".
   **对账本要按各笔的 `at` 序列比,不能比条数**: 两个账本都是**成环**的(失败痕保 20 笔 /
   现场帧保 5 笔,满了挤掉最老那笔),条数一样多而内容全换了--第一版比条数,真机上就
   漏掉了一笔新痕.

**账本上留着两笔探针造的痕**(`12:30:31` 的 `key-mismatch` = 那次相撞,`12:43:09` 的
`send-failed` = 那一撞的余波:一轮丢掉的续聊武装着,后来的一次发送也没成),各带一帧.
两笔都已被后面成功的一趟补上恢复时刻(ADR-0004 的"由红转绿").**没删**: 它们是"探针
自己也能在账本上留痕"的物证,读到的人别把它们当成产品病了.

**顺带验到的**: 失败痕的恢复("由红转绿")在真机上走通了一次--成功的一趟 `read` 之后,
先前最前面那笔的 `recoveredAt` 补上了;现场帧那一刻的配对也留在账本里(帧与痕的 `at`
逐字相等).
