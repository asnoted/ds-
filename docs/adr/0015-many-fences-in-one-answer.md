# 一次回答可以排多块围栏:一轮里各块一趟一块地打

- **Status**: accepted
- **Date**: 2026-10-04
- **Supersedes**: none

原来"一次回答最多排一块".一块就是一轮:一次出站,一次续聊,一个出站窗口
(ADR-0002/0012).模型要查三样东西就得排三轮,把"轮"这件事花在了本来一轮能做完的
活儿上--而轮数是这套东西在站点那边的**行为面**(ADR-0014 的账本).参考项目
WebTool-DeepSeek 一条回复里可以多次调用,方向一致.

## 决定

1. **检测侧全取**:`parseSendFences` 按出现顺序取出所有块;`parseSendFence` 只取第一块,
   留给"有没有排围栏"这类判据(`wait.fence`).
2. **执行侧一趟一块**:一轮里每块**各打一次**网关(不是一个请求塞多块).扩展对一条在途
   fetch 的保活与超时是**按请求**算的(`MCP_CALL_TIMEOUT_MS`);多块挤一趟,几件慢工具
   叠起来先撞扩展的超时,报出来的还是没信息量的"中继不可达".
3. **结果拼成一段**:一块时**工具正文原样交**(不加我们自己写的头尾);多块时每块前面写
   一行 `工具 <名字>:`,不然模型分不出哪段是谁说的.
4. **一轮有上限**:`MAX_CALLS_PER_ROUND = 8`,排多了先执行前 8 块,剩下的在正文里说明
   "下一轮再排".
5. **排坏的块也占一块**:那一块回 `MALFORMED_CALL_HINT`,别的块照常执行--不该因为一块
   形状不对把整轮搭进去.只有**连不上中继**才整轮作废(照旧不进对话流).

## Considered Options

- **一个请求带多块**:省往返,但超时与保活按请求算,慢工具一叠就误报成"中继不可达";
  而且中继那一侧一次 `tools/call` 就是一件工具,得为它新开一个批量形状.否决.
- **不设轮内上限**:一轮能跑几十件工具,续聊刹车(按轮计)管不到轮内.否决.
- **一块排坏整轮作废**:模型看不到别的块的结果,还得重排一遍.否决.
- **一律加 `工具 <名字>:`**:单块的正文会被我们加的头污染,而工具的原文(包括它自己报的
  错)本来就该原样给模型.否决.

## Consequences

- 同样一件活儿,轮数(= 出站次数,续聊次数)可以降到三分之一甚至更低.
- `protocol/fixtures/fence.json` 的字段从 `expectedCall` 改成 `expectedCalls`(数组),
  TS 与 pytest 两处 schema 同步改--少改一处,门就红.
- 一轮里第一块连不上中继:整轮作废(与单块时一个脾气),已经跑完的那几块结果不交回.
  宁可少一轮,也不把半个回合交给模型.
