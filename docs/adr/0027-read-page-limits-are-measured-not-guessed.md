# ADR-0027: `read` 那几个上限的实测结论:16000/200 行定案,32000 只探到没崩

- **Status**: accepted
- **Date**: 2026-10-08
- **Supersedes**: none

本篇**补 ADR-0026 的未验证项**(那四个数是拍的),并把扫法里一个**方向错误**记下来.
ADR-0026 **不因此改动**--形状一个字没动,数值回填成定案值.

## 结论先摆

**定案:`WORK_READ_PAGE_LINES = 200`,`WORK_READ_BYTES = 16_000`,扩展侧
`MAX_RESULT_CHARS = 16_000`.**(也就是 ADR-0026 原来那组数--但现在是有据的了.)

**32000 是上界探测的结果,不是定案值**:那一档没崩(0 条失败痕,offset 每步都对),
但模型**拿到答案后仍把整个文件读完**.放宽额度不会让它更精细,只会让它更浪费.

## 扫法有一个方向错误(先记,因为下次还会犯)

本篇原先写的是"从大到小扫:16000 → 8000 → 4000 → 2000",理由是"宽松的先试,才知道
天花板在哪".**那个方向找不到上界**:要找"模型读不进去"的边界得从小往上扫;从大到小
只能回答"宽松档有没有炸".

而实测把这个问题变成了另一个:**大档没炸,那么往上加也不会炸--因为约束模型的不是
额度,是那 8 轮刹车**(ADR-0015).它在第 5 轮就收手了.所以"上界"这个问题在
32000 档就已经答完:**够高,不构成约束**.

于是往下扫(8000/4000/2000)失去意义:没有证据说需要更省.

## 二分法的天花板不是 64K:那是第三方 server 的闸(**勘误**)

本篇原先写着"上界的天花板是网关那道 64K".**那是错的**,错在把两条路当成一条:

- `cap_result` 全仓**只有一处调用**(`gateway.py:482`,`Gateway._handler`),那是**第三方
  MCP server** 的结果那条路.
- **自家五件工作工具不走它**--它们经 `mcp.py:225` 的 `text_result` 直接出门,
  `text_result` 只封装不截断.

所以 `read` 原本靠 `WORK_READ_LIMIT = 16000` 兼着的那道**内存/存储闸**,在本篇删掉它之后
**是空的**.ADR-0016 的标题是"网关给交出去的东西加上限",而自家工具从来没被那道上限管过.

**已知缺口,维护者 2026-10-08 明确决定"先不管"**:四个新上限一旦被配得比旧值大,
自家 `read` 没有总量闸(内存,storage,对话三处同时被灌).补法两条--自家也走
`cap_result`,或让自家那道的截断文案**认得翻页**(`接着读:offset=`,而不是网关那句
"已截断:原文 N 字").**本篇不拍这个板.**

**所以二分没有硬天花板**,只有越撞越贵的代价.三道墙实测下来:单次预算那道人没碰到,
模型上下文那道人主动避开了,**真正撞到的是第三道--测试环境自己**.

## 撞墙记录(48000 档)

| 撞什么                                    | 结果                                                                                                                                                                                   |
| ----------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 单次预算 48000 / 每轮 48000 / 单页 700 行 | **通过**,0 条与预算相关的失败痕                                                                                                                                                        |
| 模型会不会读爆                            | **不会--它比 32000 档聪明**:3999 行的文件,它 `grep` 定位 `def f500`(得第 1997 行)再只读那 20 行,**没读完**                                                                             |
| 答案对不对                                | **三个数全对**:3999 行 / f500 在 1997 行 / 返回 `x + 500`--与造文件时的事实一致                                                                                                        |
| 页面模型上下文                            | **没碰到**(它主动用 `grep` 省了,根本没往上下文里塞大块)                                                                                                                                |
| **DeepSeek 标签页掉后台**                 | **真撞到了**:虚拟列表不挂行,`messages.*` 恒读成空(AGENTS.md 记过 2026-10-07 同一坑).修法:探针补 `page-action.py focus` 动作(`Page.bringToFront`)--任何要读页面列表的动作前都得先来一下 |

**32000 档那次"读完全文"不是预算的必然**--48000 档预算更大,它反而读得更少.所以
"放宽额度会让它更浪费"这个推论**只对那个任务成立**,不是规律.本篇原先把它写成了
一般结论,那是过度概括.

## 定案:16000 / 200 行

48000 档证明**预算给宽是安全的**(模型会自己用 `grep` 精确取点,不会顺从地读完).
所以定案仍然取 16000:同样的答案,更轻的每轮占用,而且 32000 那次"读完全文"的倾向
在更紧的预算下没出现.

**不是**因为 48000 有问题(它没问题),而是因为**没有证据需要更宽,而 16000 已经够**
--ADR-0026 那些数没变,变的是它们从"拍的"变成"验过的".

## 实测(ds-browser + 探针,2026-10-08)

同一任务问两遍(读 `dsb/work.py` 640 行,答三个具体问题),两档各跑一次.

### 16000 档(单页 200 行)

- **失败痕 0 条**.
- 模型**自己排了 `offset: 201`**(脚注给了就用),翻到 245 行收手.
- 它明确说"lines 245-264 已在前一次翻页里读到"--**正确理解了自己读过哪一段**,
  脚注三态没有误导它.
- **行号没被当成内容**:它引行号当**位置**用,且引的行号**准**
  (说 `render_page` 在 245 行,正好在那一行).

### 32000 档(单页 400 行 / 每轮 32000)

- **失败痕 0 条**;offset 每一步都对(1→201→401→601,与脚注一致).
- 三种脚注它一字不差地复述出来,还自己指出"只有后两种真的给 `offset=`"--
  **连脚注的语义边界都读懂了**.
- **但它读多了**:第 3 轮已经说"I have the answer already from lines 245-294",
  仍继续翻 601 把整个文件读完,理由是"a partial view can mislead".
  放宽到 32000 之后每页更重,**它照样读完全文**.

**上界的答案**:32000 没有让模型读不进去,也没有让它不细看--**它本来就不细看,
只是顺从地把给它的都读完了**.所以额度不是这个环节的约束.

### 顺带修掉一个真 bug(两档都跑出来的)

模型报 `dsb/work.py` 有 **625 行**,实际 **624**(`wc -l`).**脚注里那个总行数是错的,
而模型照抄了它.**

原因在 `splitlines`:用 `content.split("\n")`,而文件**以换行结尾**时那个结尾换行会多切
出一段空串,于是行数 +1.我原先的注释还写着"不丢末尾空行"--那是把"以换行结尾"
误读成了"多一行".已改为先 `removesuffix("\n")` 再切:中间的空行照旧算行,空文件回
"共 0 行".

**总数错就是模型眼里的文件错**:它拿那个数去做判断(这一档就是拿它判断"读完了没有").

## Considered Options

- **定案 48000(扫到的最大档)**:它测得**最漂亮**--模型主动 `grep` 定位,只读 20 行,
  三个答案全对.但"预算给宽是安全的"不等于"该给宽":每轮占用是实打实的成本,而
  16000 已验够用.否决--**为不存在的问题付代价**.
- **定案 32000**:没崩不等于该用,而 16000 档它 2 页就收手--**同样的答案,更轻的
  代价**.否决.
- **定案 8000 或更小**:没有证据说 16000 有问题(三档都 0 条预算相关失败),而更小
  意味着更多次翻页(每次翻页都是一轮,占那 8 轮的额度).否决--**为不存在的问题付
  代价**.
- **按 DSH 的 2000 行取用**:那是它自己仓里的默认,不是我们的答案.实测 200 行够用.否决.
- **把上界无限抬高**(比如与网关的 64K 对齐):那等于取消这道闸,而实测证明预算这一维
  本来就不构成约束(模型自己会用 `grep` 省)--**留着一个不常咬人的闸不如留着它**,
  将来真有失控结果时它还在.否决.
- **不管模型读多了**:读全文不算错,它自己判断"要确认没遗漏".但 48000 档证明**它
  不总是读多**,所以这不是需要治的行为.否决(当缺陷处理).
- **继续往上扫到撞上下文**:48000 档模型主动避开大块,上下文墙没碰到;再往上扫只会
  遇到"模型压根不用那么多"--**扫不出信息,只烧时间与账号**.否决.

## Consequences

- **四个数有了依据**:`WORK_READ_PAGE_LINES = 200`(16000 档实证够用且模型收手早),
  `WORK_READ_BYTES = 16_000`,扩展侧 `MAX_RESULT_CHARS` 与之同数.
- **`splitlines` 不再给以换行结尾的文件多算一行**,四条测试钉住这个口径(结尾有换行 /
  没有换行 / 中间空行 / 空文件).
- **"模型会不会滥用翻页"答了,而且答案是否定的**:32000 档它读完全文,48000 档(预算
  更大)它却只读 20 行--**读多少由任务决定,不由额度决定**.原先"额度会鼓励读多"那个
  推论被 48000 档推翻,本篇已改口.**额度这一维不构成约束.**
- **8 轮刹车(ADR-0015)才是这个环节的真约束**:三档都在第 5 轮以内收手,离 8 轮还远.
- **探针多了一个 `focus` 动作**(`Page.bringToFront`):读页面列表前必须先来一下,否则
  `messages.*` 恒空(后台标签页虚拟列表不挂行).这是**测出那道墙的副产品**,也是本轮
  最容易让人白跑半小时的东西.

## 未验证项

- **自家五件工具没有内存/存储闸**(上面"勘误"那节):维护者决定先不管,但**它是本篇
  删掉 `WORK_READ_LIMIT` 留下的缺口**,不是新发现的独立问题.
- **"代你发言"闸关着的半自动路径下没验**:三档都是闸开着,扩展自动发的.
- **48 行的整页渲染没在真机上出现过**:`WORK_READ_LINE_LIMIT = 500` 那条单行标注没被触发
  (造的 `longline.txt` 有 3000 字一行,但模型没去读它).
- **页比文件大的那种形状没测**:`tiny.txt` 没被模型读过,所以"文件读完"那句脚注在
  "limit 大于总行数"的情形下没在真机验过(单测验了).
- **没量成本**:各档扩展侧的实际入参长度没读数字(都没触发截断,所以"这一层的闸没咬"
  是确定的,但每轮多少字没数).
- **三档样本量不足以比较失败率**(各一两个任务),所以"0 条失败痕"只说明**没撞上
  这一类错**,不说明哪档更稳.
