# ADR-0011: 网页输入上限是按 token 计的(实测硬墙 ~98 万), 本仓按 900,000 用

- **Status**: accepted
- **Date**: 2026-10-17
  **本仓的上下文预算是单条输入 900,000 token**(`MAX_SAFE_INPUT_TOKENS`,
  `src/lib/continuation.ts`); 实测到的**硬墙**在 982,000 < 上限 < 982,700 token -- 那差出来的
  ~82,000 token **就是余量**, 不是待收窄的精度.

为什么是 token 不是字: 用 `deepseek-ai/DeepSeek-V3` 的分词器实测, 两种密度完全不同的文本
落在**同一个** token 区间(收下的最大与拒收的最小都在 [980,000, 983,785] 里): 真实中文小说
0.628 token/字, 重复单字"测" 1.000 token/字 -- 若上限按字符, 分界字数会差 1.6 倍, 不可能
收敛到同一 token 数.

## 决定

1. **预算按 token 记**: `MAX_SAFE_INPUT_TOKENS = 900_000`. 配一条测试钉住, 别被"顺手改成实测
   值"带走 -- 那是把余量删掉, 不是把精度调准.
2. **余量有具体去处**, 吸收的是我们**量不到**的部分:
   - **站点自己的系统提示词**计入总上下文, 却不在我们这条消息里, 所以"消息预算 = 总上限 −
     系统提示词"; 这一项不可见, 只能靠余量兜.
   - **服务端可以随时改**: 它是按模型/账号下发的配置(前端的 `input_character_limit` 就是这么
     下发的), 发版或灰度就能改.
   - **DeepSeek 有压缩机制的先例**(上下文超限时会话侧截断/摘要). 真上了压缩, 上限的语义会从
     "硬拒"变成"静默截断" -- 那时贴边写就是在赌它不变.
3. **只认硬判据**: 可靠的那条是 **`finish_reason`**. 拒收时服务端下发独立 error 帧
   `{"type":"error","finish_reason":"context_length_exceeded","clear_response":true}`, 那是
   秒回的一帧. "达到对话长度上限"那句话**不能单独当判据** -- 它既在拒收时出现, 也在"回复完
   了, 提示对话已满"时出现, 照它读会把结论写反. 判"收下"要看**有没有素材里没有的新文字流出
   来**(不是只看免责声明: 大消息的回复流得慢).
4. **网页其实有两道墙, 量纲不同**:

   | 墙                           | 上限                  | 量纲  | 超了的表现           |
   | ---------------------------- | --------------------- | ----- | -------------------- |
   | 服务端 token 预算(本条主题)  | ~98 万 token          | token | 回"达到对话长度上限" |
   | 前端 `input_character_limit` | 2,621,440 字(2.5 MiB) | 字符  | 拦发送 + "超长约 X%" |

   前端那道是 `localStorage` 的 `__ds_remote_feature_store_model` → `model_configs` 下发的
   配置, 三个模型(快速 / 专家 / 识图)全是这个值; 百分比 = `(len − 2621440) / len × 100`,
   只在输入超过上限, 且提交 / 粘贴触发拦截后才显示.
   两者**不随文本密度对齐到同一个数**(对中文小说前者先到; 对英文后者先到), 而且前端**根本
   没有分词器** -- 它比的是 `value.length`(字符). 所以"按哪个密度折算"这个问题本来就不成立:
   两边是两种闸, 各自独立取值. 顺带量到一条副作用: 按字符算意味着对中文它实际放行
   `2,621,440 × 3 = 7,864,320` 字节 = **7.5 MiB** 的正文.

5. **对仓库的意义**: `read` 的一页 16,000 字(~1 万 token, ADR-0010)远在 98 万 token 之下,
   不构成约束; 这道墙是"续聊 / 大段发送"场景的天花板. 它与"自家工具的内存/存储闸"是两回事.

## Considered Options

- **用字数当上限**(如"156 万字"): 密度一变就错(测字只能塞 98 万字). 上限本质是 token,
  字数只是它在某种文本下的投影. 否决.
- **用"超长约 X%"当 token 上限的判据**: 它量的是前端的**字符**上限(2.5 MiB), 不是 token
  预算, 量错对象. 否决.
- **用"达到对话长度上限"当唯一判据**: 它也出现在"回复完了提示对话已满"时. 否决.
- **钉死到个位 token**: 成本高. 否决 -- 但这条否决**当天就被推翻了**: 判据换成
  `finish_reason` 之后, 拒收是秒回的一帧(不用等回复流完), 所以当天就把界夹到了
  982,000 < 上限 < 982,700. 真正的成本大头不是等待, 是**判据要抗自污染**.

## Consequences

- **网页输入上限有了 token 口径**: 本仓预算 900,000 token / 条消息; 换算密度是真实中文小说
  ~0.628 token/字, 重复单字 1 token/字.
- **探针手法沉淀**: `scripts/page-action.py sse`(装观测 / 填 / 发 / 读**闭在一次调用里**, 按
  `finish_reason` 判拒收)与 `scripts/count-tokens.py`(离线数 token). 当时手写的一次性脚本
  已全部作废.
- **"超长约 X%"已查明**: 前端 `input_character_limit` 的百分比, 与 token 预算无关.

## 判据(怎么自己复现)

```sh
uv run pytest tests/ -q -k 'token'          # 预算常量被钉住
uv run scripts/count-tokens.py <file>       # 离线数 token(要本机有那份分词器)
uv run scripts/page-action.py sse ...       # 真机: 按 finish_reason 判拒收
```

一路踩的坑(全文搜残留渲染污染判据, 素材自带 AI 免责声明被误计成回复, `chat.new` 是 SPA 路由
切换不重载 `window`)与每种密度的边界读数见 `docs/evidence/web-input-limit.md`.

## 未验证项

- **站点系统提示词占多少 token 没数**: 它计入总上下文, 不可见, 没法直接量 -- 余量就是给它留的.
- **不同模型 / 模式是否共享这个预算没验**: 深度思考, 智能搜索开着时的预算是否相同, 未测.
- **"回复完了提示对话已满"那条路径的确切触发点没单独量**: 它和拒收共用一句话, 靠"有没有真
  回复"把两者分开了, 但前者在对话累计多少 token 后触发, 没量.
- **站点服务端按哪个分词器算没证实**: 配置里的 `normal_history_and_file_token_limit = 890880`
  与实测硬墙差 ~9.7%, 疑因分词器不同. 两条路都落在 900,000 的同一侧不影响使用, 只有哪天要改
  预算才需要回来查.
