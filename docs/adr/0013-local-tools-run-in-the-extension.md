# 组合工具住扩展侧:本地工具名册(v1 = send.page)

- **Status**: accepted
- **Date**: 2026-10-04
- **Supersedes**: none

页面动作一直没有外部调用面(ADR-0011 把 dsb→扩展 的反向通道全废了,dsb 只剩被动答).
issue #23 要的"组合功能:往页面发一个问题 → 等页面模型排围栏 → 等回灌 → 取答复",
字面写的是"组合在 dsb 侧,任何 agent 开箱即用"--但 dsb 无法反过来指挥扩展干活,
那条路在当前架构下走不通.

**决定**:组合住**扩展侧**.扩展持一小张**本地工具名册**(`src/lib/localtools.ts`):
网页模型在围栏里排 `send.page` 时,background 认出后**就地执行**(`composer.type` →
`send.enter` → `wait.fence` → `wait.reply`,全走 `runAction` 三道闸),**不把这一条
转发 dsb**;结果按回灌口径回页面.dsb 保持被动,零改动(守 ADR-0011).

## 为什么不是 dsb 侧

- dsb 是被动 MCP 网关:只能被调,不推送,无会话(ADR-0011).要让它在"组合"里指挥
  扩展打字 / 发送 / 等待,就得重开一条 dsb→扩展 的反向通道--那正是四刀刚废掉的东西.
- 页面动作执行器住在内容脚本名册里,只有 background 够得着;background 里本就有
  "组合 + 三道闸"的先例(`deliverNudge` 的 `composer.type` → `send.enter`).组合放这儿
  顺着既有经络.

## 代价与边界

- **代价**:外部 MCP agent 依旧调不到页面动作--但现状本就如此(整个动作名册都无外部
  入口),不是回退."外部 agent 直呼页面动作"要重开双向通道,是另一件事,另开任务.
- 本地名册是**扩展自己的**,不占 dsb 的 `tools/list`;协议说明(`instructions.ts`)另列
  一段"本地工具"告诉模型可以排哪些名字.
- 组合内部每一步都走 `runAction`,总开关 / 替人发言 / 退避三道闸照拦;失败码全取现成册子,
  不新增.失败以 `errorPayload` 返回,不进对话流(与 dsb 传输 / 闸失败同口径).
- 本地工具名在 background 的 `sendCall` 里截获:命中就地跑,未命中照旧转发 dsb--普通
  工具路径一字不改.
- v1 只有 `send.page`;名册扩容(如把 #30 的控件补全做成组合)先走原语路线,不急着进来.
- **`send.page` 从四步缩到两步**(2026-10-05 补记,issue #47):v1 那四步是 ADR-0014 之前画的--
  它等 `wait.fence`(页面模型排的围栏,由 `detect()` 走 `sendCalls` 处理,与本地工具这条路无关)
  与 `wait.reply`(等的是它自己触发的那轮回灌,自指),而"取答复"在 ADR-0014 把工具结果改成
  "请求体替换 + 两行短标记"之后根本做不到--**页面动作没有 MCP 工具面**,模型读不到页面消息.
  于是它每次以 `page-changed` 收场,而前两步已把消息真发出去了.缩成 `composer.type` →
  `send.enter` 两步后它只做"往页面发一条问题"这一件,`instructions.ts` 里那个"返回答复正文"
  的假承诺也一并删掉.
  **本 ADR 的机制与论证原样保留**--组合住扩展侧,`sendCall` 截获,三道闸照拦,都是对的.
- **issue #23 的原始需求仍未满足**(2026-10-05 补记):#23 要的是"组合在 dsb 侧,**任何 agent
  开箱即用**",而本 ADR 改住扩展侧之后**只对围栏里的页面模型生效**--外部 agent 依旧调不到
  页面动作(见上面"代价与边界"第一条).也就是说 `send.page` 不是 #23 的答案,它是落空的产物.
  真要满足 #23,要重开 dsb→扩展 的双向通道(ADR-0011 废掉的那条),那是**另一件事,另开任务**.
