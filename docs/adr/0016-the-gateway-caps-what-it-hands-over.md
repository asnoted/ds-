# 网关给交出去的东西加上限:结果 64K 字,单服务 128 件,三档超时

- **Status**: accepted
- **Date**: 2026-10-04
- **Supersedes**: none

`text_of_result` 的口径一直是"不猜,不丢"--结果要送进对话,模型看全貌比看半截强.
代价是**没有上限**:一条失控结果(几十兆的目录树,整份日志)会同时灌满对话,扩展的内存与
`storage`;一张塞了上千件工具的表会把协议说明撑爆;超时只有两档(握手 30s,调用 120s),
而 `tools/list` 一直借的是握手那一档--慢起来看不出是哪一档慢.

## 决定

1. **单次结果封顶**:`MAX_RESULT_CHARS = 64K 字`(按字符,不按字节--切在多字节字符中间对
   谁都没好处).超了截断并在尾巴上写明 `原文 N 字,这里是前 64K 字`,记一笔
   `result-capped tool=... chars=...`.
2. **单服务工具数封顶**:`MAX_TOOLS_PER_SERVER = 128`,超了只注册前 128 件,记一笔
   `tools-capped tool=... count=...`(记的是**原文件数**,人看得出被砍了多少).
3. **三档超时各是各的**:握手 `DSB_CONNECT_TIMEOUT`(默认 30s,npx 首次下载要时间),
   发现 `DSB_DISCOVERY_TIMEOUT`(默认 20s,一次就够),调用 `DSB_TOOL_TIMEOUT`
   (默认 120s,沿用).三个键都认进程环境与 `.env`,认不出或非正数落默认.
4. **限额打给启动日志看**:`server.py` 起服务时打一行"限额:结果 ... 字,单服务工具 ... 件,
   工具调用 ...s",生效值一眼可查.

## Considered Options

- **继续不加限**:一条结果就能把扩展的内存与存储打满,而风控与配额都跟"量"有关.否决.
- **调用档也收到 60s**:ds- 的 120s 是有意的(长工具循环要跑得住);要收紧走
  `DSB_TOOL_TIMEOUT`,不改默认值.
- **发现继续借握手那档**:一次发现没必要给 30s;分开才看得出慢在哪一档.
- **按字节截断**:多字节字符会被切两半,接在后面的正文就成了乱码.按字符.

## Consequences

- 截断处写着原长:模型知道自己看的是前多少字,会改问法,而不是拿半截正文当全貌.
- 扩展侧对**给模型看的**正文另有 2000 字截断(ADR-0014);网关这条是传输与内存的闸,
  两道各管一段,别混.
- 日志多了两个具名字段 `chars` / `count`;结果与入参的**正文**照样进不来(签名的功劳,
  不是自觉).
- 限额是常量,不当配置项:要调就改常量(有测试钉着),免得一份 `.env` 把它们改成 0.
